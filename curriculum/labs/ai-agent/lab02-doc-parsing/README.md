# Lab 2 — 한국어 금융문서 파서 비교 (Upstage vs PaddleOCR-VL)

> AI Agent 과정 / 도커·문서처리 실습 · 소요 90~120분
> 선수 지식: 파이썬 기초. GPU 없어도 진행 가능(대조군까지)

## 이 실습이 푸는 문제

OCR·파싱 실습의 진짜 난관은 모델이 아니라 **정답 데이터**입니다.
실제 약관 PDF를 구해다 사람이 라벨링하면 반나절이 날아가고, 저작권과
개인정보 문제도 따라붙습니다.

그래서 반대로 갑니다. **구조화된 데이터에서 PDF를 생성**합니다.

```
파이썬 dict  →  HTML  →  (Chromium)  →  PDF
     └────────────────────────────────→  정답 JSON
```

정답이 공짜로 따라오고, 저작권·개인정보 문제가 없으며, **난이도를 다이얼로
조절**할 수 있습니다. 벤더 벤치마크를 믿는 대신 직접 만들어 재는 것이
이 실습의 태도입니다.

## 학습 목표

- 상용 API(Upstage)와 오픈소스(PaddleOCR-VL)를 같은 자로 비교한다
- "마크다운이 예쁜가"와 "필요한 값이 맞는가"가 다르다는 것을 수치로 본다
- 벤더가 발표하는 벤치마크를 어떻게 읽어야 하는지 훈련한다
- 문서를 외부로 보낼 수 없는 환경에서 무엇이 가능한지 판단한다

## 구성

```

│   ├── templates.py     문서 4종 (난이도 L1~L4)
│   ├── generate.py      HTML → PDF + 정답 JSON

├── parsers/
│   ├── base.py          어댑터 인터페이스 ← 수강생이 여기에 추가
│   ├── upstage.py       Upstage Document Parse (상용 API)
│   ├── paddleocr_vl.py  PaddleOCR-VL (오픈소스 로컬)

├── score.py             채점기 (의존성 없음)

```

## 난이도 설계

| 레벨 | 문서 | 함정 |
|---|---|---|
| **L1** | 보험 가입내역 | 선이 있는 단순 표. **모든 파서가 통과해야 하는 하한선** |
| **L2** | 요약 손익계산서 | **선 없는 표**, 음수 괄호 `(41,220)`, 우측정렬 숫자 |
| **L3** | 청약서 | 2단 레이아웃(읽기 순서), ☑/☐ 상태, 각주 |
| **L4** | 스캔본 | L2와 내용 동일. **텍스트 레이어가 없는 이미지 PDF** |

L4는 CSS 필터로 만드는데, Chromium이 이를 래스터화해서 **실제로 문자 정보가
0인 PDF**가 나옵니다(`chars: 0, images: 1`). 스캔본을 정확히 재현합니다.

## 채점 방식 — 세 지표를 따로 봅니다

종합 점수 하나로 뭉개지 않는 것이 요점입니다.

| 지표 | 무엇을 재는가 |
|---|---|
| **텍스트↓** | 글자를 제대로 읽었는가 (낮을수록 좋음) |
| **표** | 표의 행/열 구조를 유지했는가 (셀 단위 정확도) |
| **필드** | 앵커 주변에서 **실무에 필요한 값**을 정확히 뽑았는가 |
| **체크** | ☑ / ☐ 를 구분했는가 (L3만) |

### 텍스트 지표를 CER로 재지 않는 이유

처음에는 문서 전체 CER(문자 오류율)로 만들었는데, 대조군이 **본문과 표를
다른 순서로** 내놓자 30% 오류로 찍혔습니다. 두 문자열 길이는 264자로 동일,
즉 읽기는 완벽하고 배치만 달랐습니다.

> exact-match 계열 지표는 구두점·줄바꿈·블록 순서 같은 **무해한 차이에
> 벌점**을 줍니다. 2026년 OCR 벤치마크 논쟁의 핵심 쟁점이 바로 이것입니다.

그래서 정답을 줄 단위로 쪼갠 뒤 각 줄이 출력 어딘가에 얼마나 정확히
들어있는지를 재고 길이로 가중 평균합니다. 순서에 무관하고 글자 오류에는
민감한 지표입니다. 같은 출력의 점수가 30.3% → 0.0%로 바뀌었습니다.

**수업에서 이 이야기를 꼭 하세요.** "벤치마크 숫자를 만들 때 무엇을 잘못
재기 쉬운가"를 실제 사례로 보여줄 수 있는 대목입니다.

## 진행 순서

### Step 0. 준비 (10분)

```bash
make dataset          # 폰트 자동 다운로드 + 문서 4종 생성
make preview          # 미리보기 PNG (수업 화면에 띄우기 좋음)
```

Chromium 경로가 다르면 `export CHROME_PATH=/usr/bin/chromium`.

### Step 1. 채점기부터 검증 (15분)

```bash
make test
```

**파서를 비교하기 전에 자를 먼저 재봅니다.** 정답을 그대로 넣으면 만점,
표에서 2행을 빼면 표 점수만 떨어지고, 20자마다 오타를 내면 텍스트 점수만
떨어지는지 확인합니다. 5개 케이스 × 4개 문서 = 20건이 모두 통과해야 합니다.

> 이 단계를 건너뛰면 뒤의 모든 비교가 무의미합니다. 실무에서 평가 코드를
> 먼저 테스트하지 않아 잘못된 결론을 내는 일이 흔합니다.

### Step 2. 대조군 먼저 돌리기 (15분)

```bash
pip install pdfplumber
python3 run_compare.py --parser pdfplumber --save
```

```
문서                 파서            텍스트↓      표     필드     체크     종합
L1_보험가입내역        pdfplumber      0.0   100.0  100.0    -    100.0   행 5/5 매칭
L2_요약손익계산서      pdfplumber      0.0     0.0  100.0    -     70.0   표를 찾지 못함
L3_청약서             pdfplumber      7.7   100.0  100.0  100.0   98.3   행 4/4 매칭
L4_스캔_요약손익계산서  pdfplumber    100.0     0.0    0.0    -      0.0   출력 없음
```

**여기서 이미 절반은 가르쳐집니다.**

- **L1은 대조군도 만점입니다.** 선이 있는 단순 표에 돈을 낼 이유가 없습니다.
- **L2에서 표가 0점**입니다. 선이 없으니 `extract_tables()`가 아무것도 못
  찾습니다. 그런데 **텍스트는 0% 오류, 필드도 100%**입니다 —
  "글자는 다 읽었는데 표가 아니게 됐다"는 상태를 정확히 보여줍니다.
- **L4는 전부 0점.** 문자 정보가 없으니 OCR 없이는 불가능합니다.

수강생에게 먼저 물어보세요. **"어느 레벨부터 돈을 내야 할까요?"**

### Step 3. Upstage 붙이기 (20분)

```bash
export UPSTAGE_API_KEY=up_...
python3 run_compare.py --parser upstage --save
```

확인할 것:
- L2의 **선 없는 표**를 표로 복원하는가
- 음수 괄호 `(41,220)`를 `-41,220`으로 바꿔버리지 않는가 (필드 채점에서 드러남)
- L3의 ☑/☐ 를 구분하는가
- L4 스캔본에서 몇 점이 나오는가

### Step 4. PaddleOCR-VL 붙이기 (25분)

```bash
pip install paddleocr paddlepaddle      # GPU면 paddlepaddle-gpu
python3 run_compare.py --parser paddleocr-vl --save
```

최초 실행 시 모델을 수 GB 내려받습니다. **강의 전에 미리 받아두거나 강사
이미지에 포함시키세요.** 이것 자체가 "오픈소스의 숨은 비용"입니다.

### Step 5. 나란히 놓고 판단 (20분) ← 하이라이트

```bash
make compare
```

`out/` 에 파서별 원본 출력이 남으니, **점수가 갈린 지점의 실제 출력을 열어
비교**하게 하세요. 숫자만 보면 배우는 게 없습니다.

토론 질문:

1. L1~L2만 다루는 업무라면 무료 대조군으로 충분한가?
2. 스캔본(L4) 비중이 30%인 조직이라면 판단이 어떻게 달라지는가?
3. **문서를 외부 API로 보낼 수 없는 규정**이라면 선택지가 무엇인가?
   (이 질문이 금융권에서는 성능보다 먼저 옵니다)
4. 페이지당 단가 × 월 처리량 vs GPU 서버 비용, 손익분기점은 어디인가?

### Step 6. 수강생 과제

`parsers/base.py` 의 `Parser` 를 상속해 파서를 하나 더 붙입니다.
`available()` 과 `parse()` 두 개만 구현하면 자동으로 비교표에 들어옵니다.

후보: Mistral OCR, Docling, Gemini/Claude 직접 호출, AWS Textract,
사내 솔루션.

추가 과제: `docgen/templates.py` 에 **본인 업무 문서를 닮은 L5** 를 만들기.
정답을 함께 정의해야 하므로, 이 과정에서 "내 업무에서 정확해야 하는 필드가
무엇인가"를 스스로 정리하게 됩니다.

## 알려진 한계 (반드시 함께 언급할 것)

- **합성 문서는 실제 문서보다 깨끗합니다.** 진짜 스캔본에는 접힌 자국, 도장,
  손글씨, 이중 인쇄가 있습니다. 여기 점수가 실무 성능의 상한선이라고
  생각하세요.
- **L4는 진짜 스캔이 아니라 래스터화된 렌더링**입니다. 문자 레이어가 없다는
  성질은 같지만 노이즈 특성은 다릅니다.
- **표본이 4건**입니다. 순위를 매기기엔 턱없이 적습니다. 실제 도입 판단은
  본인 문서 수백 건으로 다시 재야 합니다.
- **필드 채점은 앵커 근처 120자 윈도우** 안의 문자열 일치입니다. 값이 우연히
  근처에 있으면 맞았다고 셉니다. `score.py` 의 `FIELD_WINDOW` 를 줄여가며
  점수가 어떻게 변하는지 보게 하면 좋은 토론거리가 됩니다.
- **비용은 채점하지 않습니다.** 페이지당 단가와 지연시간은 별도 표로 정리해
  함께 놓고 판단해야 합니다.
