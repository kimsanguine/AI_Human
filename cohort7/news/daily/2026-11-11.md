**출처:** [GitHub — Graphify-Labs/graphify (GitHub Trending Python 주간 목록 확인 — 2026-11-11)](https://github.com/Graphify-Labs/graphify)

프로젝트 폴더 하나를 넣으면 코드와 문서, DB 스키마, 설정 파일, PDF 사이의 관계를 그래프로 엮어 줍니다. 코드는 tree-sitter 기반 AST 파싱으로 LLM 없이 로컬에서 결정적으로 분석하고, 그래프의 연결(엣지)마다 "왜 연결됐는지" 근거를 남깁니다. Claude Code·Cursor·Codex·Gemini CLI에서 `/graphify` 스킬로 실행하며, 벡터 스토어를 쓰지 않는 것이 특징입니다.

> **학습 연결:** Ch09에서 배운 '벡터 유사도 검색 기반 RAG'와 달리, 이 레포는 **지식 그래프 RAG**처럼 엔티티 간 관계(호출·참조·스키마)를 따라가며 문맥을 찾기 때문에 "임베딩이 비슷한 청크"가 아니라 "구조적으로 연결된 근거"를 에이전트에 넣는 방식을 직접 비교해 볼 수 있습니다.

### 2. [📰] 페이팔, "모델은 그대로 두고 지식 레이어만 붙였더니" 사내 AI 어시스턴트 정확도 43% → 95%
**출처:** [VentureBeat — 2026-11-10](https://venturebeat.com/orchestration/paypal-says-its-ai-assistant-went-from-43-to-95-accuracy-without-changing-the-model)

페이팔은 데이터 분석 어시스턴트의 LLM을 바꾸지 않고, '골든 쿼리'(목적별 정답 조회 쿼리)와 '분석 플레이북'(질문을 어떤 순서로 조사할지)을 모델과 분리된 지식 레이어로 붙여 정확도를 43%에서 95%로 올렸다고 밝혔습니다. 모델이 바뀌어도 지식은 그대로 재사용하려는 설계이며, 사내 HR 질의응답에서는 절차의 단계를 청크로 쪼개면 답이 틀려져 '순서가 있는 단계는 한 덩어리로' 저장하는 방식으로 바꿨다고 합니다.

> **학습 연결:** Ch09 **청킹 전략**과 Ch08 **메모리·도구 호출 설계**의 실전 사례로, "같은 데이터에 접근해도 '신규 계정' 같은 업무 정의를 검색해 넣어 주지 않으면 답이 틀린다"는 점이 RAG에서 검색 대상(무엇을 인덱싱할지)을 정하는 일이 모델 선택보다 먼저라는 것을 보여 줍니다.

### 3. [📰] 엔비디아 논문 "긴 문맥, 꼭 필요한가?" — 대화를 중간 요약해 16K로 줄여도 에이전트 성능 대부분 유지
**출처:** [ZDNet Korea — 2026-11-10](https://zdnet.co.kr/view/?no=20261110210319) · 원문: [arXiv:2611.05306](https://arxiv.org/abs/2611.05306)

엔비디아 연구진은 256K 문맥으로 서비스하면 16K 대비 생성 토큰당 비용이 모델에 따라 3.6~7배까지 커진다고 분석했습니다. 긴 작업 중간에 대화를 요약해 줄이는 방식을 22개 설정으로 시험한 결과, 기준보다 2점 넘게 떨어진 경우는 5개 이하였고, 긴 문서 질의(LOONG)에서는 필요한 부분만 골라 읽은 쪽이 평균 70.1점 → 79.3점으로 더 높았습니다. 다만 일부 코딩 모델은 성공률이 53.0%에서 3.6%로 무너져 모델별 편차가 컸습니다.

> **학습 연결:** Ch06에서 배운 **어텐션 연산 비용이 문맥 길이에 따라 커지는 구조**와 Ch09 **"전부 넣기 대신 골라 넣기(검색·요약)"** 원칙을 숫자로 확인시켜 주는 연구로, 컨텍스트 윈도우 크기 경쟁보다 무엇을 남기고 요약할지가 비용·정확도를 좌우한다는 근거가 됩니다.
